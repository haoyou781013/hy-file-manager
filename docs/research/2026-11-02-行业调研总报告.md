## 第一部分 · 行业全景

### 竞品横向对比

| 产品 | 信息架构 | 独有能力 | 收费 |
|---|---|---|---|
| **MT管理器** | 双窗口并列 | APK 反编译、Dex编辑器++、Arsc编辑器、去签名校验、SFTP/SMB/WebDAV、APK MCP | 免费 + 逆向工具会员（约 99–135 元买断） |
| **MiXplorer** | 多标签 + 横屏双面板 | 20+ 网盘聚合、内置 FTP/SFTP/SMB **服务器**、定时任务、查重 | 免费（需装插件）≈ 付费版 |
| **Solid Explorer** | 双栏 + 云 | 云盘、指纹加密文件夹、Root | 试用后买断 |
| **FX File Explorer** | 单窗 + 可选双窗 | 网络、媒体管理、Root | 免费 + Plus 买断 |
| **X-plore** | **双栏树形**（行业唯一） | Disk Map、SSH Shell、PC 浏览器访问、SQLite 查看器、Vault、Zip 当目录 | 免费 + 9 项付费 |
| **ZArchiver** | 单栏 | 格式覆盖最广、分卷、加密 | 免费 + 去广告 |
| **Files by Google** | 单栏 + 分类 | 智能清理 | 免费 |
| **ES 文件浏览器** | 单栏 + 侧栏 | 曾以 SMB + 应用管理起家 | **已衰落**（2019 年 Google 下架 DO Global 全线） |

### 关键结论

1. **双栏是行业默认，不是差异化** — MT / Solid / FX / X-plore / MiXplorer 全部提供。我们已有双窗格，**方向正确**。

2. **但双栏的行业标准交互是「栏间按钮条」** — X-plore 在两栏之间放一条可配置按钮栏，按钮按可用性自动启停，长按 Copy = Move。
   **我们用「底部同步箭头 + 多选 opBar」，操作时视线要离开两栏去底部，是可用性劣势。**

3. **归档/网络存储「当目录浏览」是易忽略的标配** — X-plore 把 Zip 渲染成普通文件夹。
   我们已有 `zip://` 虚拟路径，方向正确；X-plore 提示「从大 Zip 操作会慢（需重压缩）」，我们只读浏览，需确认性能提示。

4. **回收站已是标配，MT 踩坑值得抄** — MT 从 v2.15.6 起有总开关 + 保护范围，社区有「误删全部照片找不回」的求助。
   **我们有 `trashDefault` 开关 + `trashKeepDays`，但无「保护范围」。**

5. **多选哲学：X-plore「always available, yet not disturbing」** — 勾选框常驻但不抢视觉。
   我们「横滑进多选」是创意，但**行业无先例 = 用户不会发现**。已核实：**长按也能进多选**，这条没问题。

6. **万级目录：开源项目普遍翻车** — Fossify File-Manager 有未修复 issue：9000–10000 文件目录反复开关后位置重置并崩溃（2024-01 至今 open）。

7. **收费模式三种通行解，无一家用订阅制** — 买断（Solid/FX）、免费+会员解锁垂直能力（MT）、免费+捐赠（X-plore）。**订阅是反常的。**

8. **ES 的衰落是治理问题不是功能问题** — 功能再强，商业模式出问题就归零。

9. **MT 的盗版生态是一面镜子** — B 站一周 26 条 MT 视频 10 条在推「永久会员安装包」，盗版包无法更新补丁。**做付费必须假设会被改包。**

10. **不要拿 Files by Google 当竞品** — 无网络存储、无 Root、无双栏，定位是「清理工具」。

11. **终端内置是极小众能力** — 11 个产品中只有 MiXplorer（需外部终端）和 X-plore（SSH Shell）提供。**我们的内置终端是差异化点。**

12. **MT 单独分发「TargetSdk28 版」** — 只能从官网下载、不上架商店，用于旧机型/规避新存储限制。

## 第二部分 · 动效规范（核心）

### 2.1 Material 官方时长 token

```
short1=50  short2=100  short3=150  short4=200
medium1=250  medium2=300  medium3=350  medium4=400
long1=450  long2=500  long3=550  long4=600
extralong1-4 = 700 / 800 / 900 / 1000
```
> **duration 应取自这组 token，不要写 180/240/520 这类散值。**

### 2.2 四个关键阈值【官方原文】

| 场景 | 时长 |
|---|---|
| 常规转场 | **300ms** |
| 大/复杂全屏转场 | 最长 **375ms** |
| **进入**屏幕的元素 | **225ms** |
| **离开**屏幕的元素 | **195ms** |
| **感知为慢的红线** | **> 400ms** |

原文：「Transitions that exceed 400ms may feel too slow」

### 2.3 缓动曲线 → Android Interpolator

| Material | Android | cubic-bezier |
|---|---|---|
| standard | `FastOutSlowInInterpolator` | (0.4, 0, 0.2, 1) |
| decelerate（入场） | `LinearOutSlowInInterpolator` | (0, 0, 0.2, 1) |
| accelerate（离场） | `FastOutLinearInInterpolator` | (0.4, 0, 1, 1) |
| emphasized 减速 | — | (0.05, 0.7, 0.1, 1) |

### 2.4 stagger 的官方判据【官方原文】

M1 Choreography 三条原文：
1. 「Do: List items have a **slightly** staggered entrance.」
2. 「**Don't**: Items **shouldn't appear within the list all at once.**」
3. 「**Don't**: Do not wait for each item to fully animate before introducing the next item. **Begin each item's staggered entrance no more than 20ms apart.**」

> **判据 = 相邻两项延迟 ≤ 20ms，且下一项不等上一项播完。**

**合法场景仅限「新建 surface」**：首次进入列表、新建文件夹后刷新、空态→有内容。
**翻目录 / 下拉刷新 / 排序不属于 creation，不应 stagger。**

### 2.5 「过度动画」判定标准（综合归纳）

| 判据 | 阈值 | 性质 |
|---|---|---|
| 时长超标 | 单次 > 400ms | 【官方原文】 |
| stagger 超标 | 单项间隔 > 20ms | 【官方原文】 |
| 并发超标 | 同屏 ≥3 个独立动画 | 【经验判断】 |
| 重复播放 | 无状态变化时重播 | 违反 creation 原则 |
| 打断重播 | 连续翻目录每次重播入场 | 感知为卡顿 |

> ⚠️ **术语澄清**：Material 官方规范中**没有 "over-animation" 这一术语**。
> 业界用 "excessive motion" / "animation overload"。对外建议用「动效过多 / 时长超标」。

### 2.6 刷新导致整列表重播的诊断【官方源码】

RecyclerView 源码注释：
> `notifyDataSetChanged()` **不会触发** ItemAnimator

「整表重播」几乎一定来自：**重建 Adapter / 重设 LayoutManager / 重新 setAdapter()**，或对每项手动 `animate()`。

### 2.7 性能红线

**掉帧三大原因：**
1. **动画属性触发 layout pass** — 动 `width/height/margin/padding` → 每帧 measure+layout+draw。
   **必须只动 `translationX/Y`、`alpha`、`scaleX/Y`、`rotation`**（走 RenderNode，只重绘不重布局）
2. **`onDraw` 中 alloc** — 每帧 `new Paint()` / `new RectF()` → GC 抖动
3. **用 View 动画而非属性动画** — 点击热区不跟随，无法中断

**性能优先序**：`ViewPropertyAnimator`（`view.animate()`，最轻）> `ObjectAnimator` > `TransitionManager` > **MotionLayout（最重）**

### 2.8 必须响应 `ANIMATOR_DURATION_SCALE`

```java
float scale = Settings.Global.getFloat(getContentResolver(),
        Settings.Global.ANIMATOR_DURATION_SCALE, 1f);
```
- 系统 `ViewPropertyAnimator` / `ObjectAnimator` **会自动**受该值缩放
- **但 `postDelayed(240)` 手写延时不会被缩放** → 动画缩到 0，回调仍等 240ms
- Android 14+ 无障碍「移除动画」（`accessibility_force_reduce_motion`）**不改**这个值，需另行读取

### 2.9 Predictive Back【官方】

- Android 14 引入，15 对 targetSdk 35 默认启用，16 起成平台默认
- 需显式 `android:enableOnBackInvokedCallback="true"`
- **不注册 `OnBackInvokedCallback`，系统手势返回会绕过应用导航栈，直接退 Activity**

## 第三部分 · 功能架构（关键架构债）

### 3.1 `MANAGE_EXTERNAL_STORAGE` 是唯一完整路线【官方原文】

官方把「**文件管理器**」列为可申请该权限的用例**第一位**：
> 其他用例（如**文件管理器应用**、备份和恢复应用以及文档管理应用）也需要考虑类似情况。

覆盖：共享存储所有文件、**USB OTG 和 SD 卡根目录**、除 `/Android/data/` 外的全部内部存储。
**例外**：其他应用专用目录仍不可访问。

**Play 政策合规风险低**，需提交声明表单。

### 3.2 为什么 Android 11+ 功能缩水【官方原文】

targetSdk ≥ 30 时 `ACTION_OPEN_DOCUMENT_TREE` **不能**申请：
- 内部存储卷根目录
- **各 SD 卡卷根目录**
- `Download` 目录
- `Android/data/`、`Android/obb/` 及全部子目录

> **不是厂商懒，是平台设计。** SAF 是「逐目录授权」，文件管理器要「打开就看见整机」，两个模型不兼容。

### 3.3 ⚠️ Android 15 前台服务 6 小时上限【官方原文，本项目已踩线】

> 如果应用以 Android 15 或更高版本为目标平台…系统允许 dataSync 和 mediaProcessing 前台服务在 **24 小时内总共运行 6 小时**，之后调用 `Service.onTimeout(int, int)`。

`dataSync` 官方定义含「**Local file processing**」「Import or export operations」——**正是文件复制和压缩**。

### 3.4 inSampleSize 官方算法【官方原文】

```java
while ((halfHeight / inSampleSize) >= reqHeight
        && (halfWidth / inSampleSize) >= reqWidth) {
    inSampleSize *= 2;
}
```
量化：**2048×1536 用 sample=4 → 0.75MB 而非 12MB，20 倍差距。**

### 3.5 目录扫描三种 API

| API | 适用 | 限制 |
|---|---|---|
| `File.listFiles()` | **有 MANAGE 权限时最优** | 无权限时只能看自己目录 |
| `MediaStore` | 媒体库聚合 | 只覆盖已入库媒体，**文件名搜索不能用** |
| `SAF`/`DocumentFile` | 用户点选后持久访问 | **极慢**，必须用 `DocumentsContract` 批量 query |

### 3.6 跨存储的坑

- **跨卷 `rename` 必然失败（EXDEV）**，必须降级为「复制+删除」
- FAT32/exFAT 不支持：POSIX 权限、符号链接、文件名含 `:*?"<>|`、单文件 >4GB
- **mtime 精度**：FAT32 只有 2 秒
- **拔出 U 盘**：`IOException` 而非可预测错误

### 3.7 Android 13/14 权限变化

- **13**：`READ_EXTERNAL_STORAGE` 拆成 `READ_MEDIA_IMAGES` / `VIDEO` / `AUDIO`
- **14**：新增「部分照片访问」`READ_MEDIA_VISUAL_USER_SELECTED`
  → **扫描器不能假设「授权＝全量可见」**

## 第四部分 · 本项目代码核对

### 4.1 动画现状

| 项 | 实测 | 结论 |
|---|---|---|
| 动画调用总数 | **53 处** | — |
| 时长区间 | 60–280ms，中位数 ~150ms | ✅ 合理 |
| 超 250ms | 仅 1 处（280ms 缩放回弹） | ⚠️ 轻微超标 |
| `ANIMATOR_DURATION_SCALE` | **未读取** | ❌ 无障碍不合规 |

### 4.2 发现的问题

#### P1 · stagger 每次 reload 都播（违反官方规范）

位置：`FileManagerModule.java:2112`
```java
playStaggerAnimation(p.list);   // reload() 末尾，无任何条件判断
```

内部：
```java
child.animate().alpha(1f).setDuration(90).setStartDelay(i * 12L).start();
```

- 官方明确 stagger 仅限「新建 surface」，**翻目录/排序/删除后刷新都不应播**
- 12ms/项 ≤ 官方 20ms 上限，**这一条本身合规**
- 只对可见子项（约 8–12 项）生效，最大延迟 ~120ms，**影响可控**
- 但**每次 reload 都播**，连续翻目录时反复重播 = 「打断后重播」，被点名的过度动画

#### P2 · ItemAnimator 四个时长不在 M3 token 台阶上

位置：`FileManagerModule.java:1069-1075`
```java
ia.setAddDuration(180);      // 应为 150 或 200
ia.setRemoveDuration(160);   // 应为 150
ia.setMoveDuration(180);     // 应为 150 或 200
ia.setChangeDuration(160);   // 应为 100 或 150
```
M3 token 里没有 160、180。**这是最易改的一处。**

#### P3 · 无 ForegroundService（Android 15 架构债）

- 全项目**无** `startForeground` / `foregroundServiceType`
- 压缩/解压跑在 `runTask()` 自建线程池
- **targetSdk 升 35+ 后，大任务会被杀且无进度持久化**

#### P4 · 未适配 Predictive Back

- 无 `OnBackInvokedCallback` / `onBackPressedDispatcher`
- 用自建 `backStack` 双窗格导航
- **Android 16 起系统手势返回会绕过导航栈直接退 Activity**

#### P5 · inSampleSize 偏离官方

`ThumbLoader.java`：
```java
private static int sampleSize(int w, int h, int target) {
    int s = 1;
    while (w / s > target * 2 && h / s > target * 2) s *= 2;
    return s;
}
```
- 用 `AND` 条件，官方用 `>=` 且分别判断
- 目标尺寸 `target * 2` 比官方保守（解码更小，质量略低但省内存）
- **不算 bug，但偏离官方；需实测确认缩略图是否清晰**

#### P6 · 跨卷 rename 已有降级（合规）

`FileOps.java:113-127`：
```java
if (src.renameTo(dest)) { ... }
copyRecursive(src, dest);   // 跨分区
deleteRecursive(src);
```
✅ **已正确实现 EXDEV 降级**。

### 4.3 已核实合规

| 项 | 状态 |
|---|---|
| 长按进多选 | ✅ `FileListAdapter:184` |
| 回收站开关 + 保留天数 | ✅ `trashDefault` / `trashKeepDays` |

|---|---|
