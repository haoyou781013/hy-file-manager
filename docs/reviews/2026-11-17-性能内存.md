# HY文件管理 性能/内存审查

范围：FileManagerModule.java (17224 行) + FileListAdapter / ThumbLoader / ZipCache / ImageViewerActivity / FileOps / AccessUtil。已达标项：dirCache LRU24、archiveItemsCache LRU8、历史栈上限50、undo 上限200条/32MB、ThumbLoader 3线程池+8MB LruCache+磁盘200MB/30s节流trim、PREF_HANDLER 后台落盘、ZipCache 300MB LRU+退出即删、回收站清扫后台化。以下为存量问题。

## P0

**P0-1 主线程同步 listFiles/stat（导航+刷新+启动）**
- 点：`FileManagerModule.java:1783` 注释自认"文件列表本身就是同步 listFiles"；`reloadAll()` 2919 → `createMainView` 1088 首帧前执行；下拉刷新 1781 同步 reload。
- 量化：万级目录一次 listFiles 100~500ms+；启动白屏首帧延迟同量级；每次刷新/导航重复。
- 修复：后台线程 listFiles → 主线程只 apply 数据；启动时先渲染壳 + 骨架，异步填列表。
- 风险：高（用户可感卡顿）。

**P0-2 onBindViewHolder 每行重分配（滚动手感主因）**
- 点：`FileListAdapter.java:297-370`。每行绑定：`makeBg` 562 新建 GradientDrawable；`UiKit.color` (UiKit.java:179) 每次 new TypedValue+resolveAttribute，每行调 4~8 次；`buildSub` → `formatDate` (AccessUtil.java:67) 每次 new Date + 2×Calendar.getInstance（fileYear 无缓存）；`formatSize` (AccessUtil.java:20-24) 每行 String.format；`supports()` (ThumbLoader.java:74) 每行 toLowerCase 全名；`isPackageDir` 145 + `appIconFor` 183 首查时主线程 Binder IPC。
- 量化：一屏 15~20 行 ≈ 800~1200 个临时对象/帧 + 每次 formatDate ~10~30µs；快速滚动掉帧。
- 修复：SubText/颜色/图标属性在 FileEntry 构建时预计算并缓存（失效由 reload 清）；UiKit.color 加 attr→int 静态缓存（主题切换时清）；fileYear 缓存 Calendar 字段。
- 风险：高。

**P0-3 排序 comparator 内重复 toLowerCase**
- 点：`FileManagerModule.java:3234-3248` naturalCompare 每次比较对两个文件名 toLowerCase；名排序 `sortEntries` 每次 reload 全量重排。
- 量化：1 万文件 ≈ 13 万次比较 × 2 次字符串分配 ≈ 26 万对象、~10MB 抖动 + GC 停顿，主线程执行。
- 修复：Schwartzian transform——先对每个 name 算一次 lowerKey（存 FileEntry.sortKey），再比较；或按需缓存。
- 风险：高（大目录进目录秒级卡顿）。

**P0-4 任务队列无界 + 裸线程**
- 点：`TASK_QUEUE` (FileManagerModule.java:120) `newSingleThreadExecutor` 默认无界队列，`queuedTasks` 仅计数不限制，连续触发粘贴/解压可无限排队且逐任务起前台服务；`FileOps.runAsync` (FileOps.java:216) 7 个调用点每次 new Thread，批量操作线程数无上限。
- 量化：用户连点 20 个解压任务 → 20 个 Runnable 串行积压 + 20 次 acquire/release；FileOps 并发大复制峰值线程数=任务数。
- 修复：队列加 maxPending 上限（超限去重/拒绝）；FileOps 换共享线程池；TASK_QUEUE 任务去重合并。
- 风险：高（内存+ANR 面）。

## P1

**P1-1 主线程 commit 残留**：`FileManagerModule.java:1545` 排序菜单 `edit().putInt(...).commit()` 在 onClick 主线程；`6882` 设置清除同理。量化：每次 5~30ms fsync。修复：改走已有 `PREF_HANDLER`（437 行封装现成）。风险：中。

**P1-2 ZipCache.trimIfNeeded 每次解出全盘扫描**：`ZipCache.java:150` extract 成功路径每文件调 trimIfNeeded → 220-260 全扫 4 个缓存目录 + listFiles + 全量 sort，且发生在 synchronized 锁内（其它同 key 请求阻塞）。量化：解 500 条目的包 = 500 次目录扫描；解大文件（视频）时锁内扫盘放大写延迟。修复：照 ThumbLoader 做字节累加 + 30s 节流，或 trim 移出锁。风险：中。

**P1-3 查看器解码线程与峰值内存**：`ImageViewerActivity.java:417` 每次翻页 new Thread 解码，无 in-flight 控制，快速翻页并发解码；650 hdMode 默认 ARGB_8888 2×屏（单张上限 16MP≈64MB）+ offscreenPageLimit=1 三页常驻。量化：快速滑动峰值 3~5 张×64MB≈200~320MB，低端机 OOM。修复：单线程解码队列+序号淘汰（部分已有 mySeq）；翻页丢弃即 recycle；超高清图改用 BitmapRegionDecoder 分块（594 注释承认 0 处使用）。风险：中高。

**P1-4 LOCKS 表不清理**：`ZipCache.java:149` 注释明示"锁对象不清理"；trimIfNeeded 删文件时不移 LOCKS，仅 purgeArchive 移。量化：长会话解出 N 条目 → N 个 Object 常驻（小但无界）。修复：trim 删除成功后同步 LOCKS.remove。风险：低。

## P2

**P2-1 String.format 热路径**：`AccessUtil.java:20-24` formatSize 用 String.format(Locale, ...)（Formatter 解析+装箱），每行 bind 一次。修复：手写数值格式化或缓存 2 位小数表。风险：低（滚屏放大）。

**P2-2 相册扫描裸线程**：`FileManagerModule.java:4662-4676` 每子目录 listFiles + `getName().toLowerCase()` 逐文件（文件名小写化应复用 ThumbLoader 语义）。一次性，影响有限。修复：复用线程池 + extOf。风险：低。

**P2-3 启动全量 View 构建**：`createMainView` → `buildContent` 1653 同步建全部页（文件列表/侧边栏/编辑器骨架）。量化：冷启动 UI 构建 ~10~30ms。修复：非首屏容器惰性创建。风险：低。

**P2-4 编辑器 onPause 裸线程+commit**：`FileManagerModule.java:749-777` 每 tab 全量写草稿 + 24 键 commit 在 new Thread（不卡 UI 但每次 onPause 起线程+fsync）。修复：走 TASK_QUEUE + 脏检查。风险：低。

## 最值得改的 3 项
1. **P0-2** 行绑定缓存化（预格式化副文本/颜色/图标）——滚动流畅度立竿见影，纯前端改造。
2. **P0-3** 排序 key 预计算——大目录进目录卡顿的根因，改动小（10 行）。
3. **P0-1** listFiles 移出主线程（含启动异步首屏）——启动白屏与导航卡顿的根因，需小心线程切换与缓存失效，工作量最大但收益最高。
